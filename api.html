# AppLab

> Deploy an application to Kubernetes by uploading its source. You get back a
> URL. There is no Dockerfile you must write by hand, no CI to configure, no
> registry to push to and no manifest to apply.

AppLab owns the whole path from a local working directory to a running
application: it stores your source in a git repository it hosts, builds an image
from it in a build Job inside the cluster, deploys that image, and exposes it on
a hostname. One HTTP call starts that path; one call streams the build log; one
call tells you what is running.

Two things are enough to use it: **the base URL** and **an API key**.

## The shape of it

    upload source ──▶ build image ──▶ deploy ──▶ https://<app>.<domain>

Each step is idempotent and observable. You can upload again to redeploy, watch
a build's log while it runs, and roll back to any earlier upload without
rebuilding it.

## Start here

    curl -sS "$APPLAB_URL/api/v1/config"

That needs no key, so it is the cheapest way to check the URL is right and to
read back this deployment's limits and its default domain. Then create an app
and push code to it — see the API reference at the end of this file.

## What applab is not

It is not a general-purpose Kubernetes client. It manages the resources of the
apps you create through it and nothing else, and it confines itself to the one
namespace it runs in. Reaching for it to inspect or change anything else will
not work.

## Concepts

### An app

An app is the unit of everything: one source repository, one image, one
Deployment, one address. Its **id** is how you refer to it everywhere, and it is
immutable — there is no rename, so nothing has to be rewritten when it changes.

An id has to survive being a URL path segment, a git repository directory and a
Kubernetes object name, so it is constrained to what is valid as all three:
lowercase letters, digits and dashes, starting with a letter or digit, at most
40 characters. Some names are reserved because they would collide with this
service's own routes.

### Source is a git repository

Every app's source lives in its own git repository, hosted here. Uploading a
tarball of your working directory writes a commit to it — the tarball is how the
bytes travel, the commit is what is recorded.

That matters because it means the source is real: you can clone it, see its
history, diff two uploads and roll back by deploying an earlier commit. If this
service were lost, the repositories would still be readable with ordinary git
tools.

Uploading a tarball rather than pushing over git is deliberate: a plain HTTP
upload works from anywhere, including from an agent or a container that has no
git credential and no way to navigate an interactive auth prompt.

### Commits are what you deploy

A deploy names a commit. Rolling back means deploying an earlier one — and if
that commit was built before, its image already exists and is reused rather than
rebuilt, so a rollback is fast and cannot fail for a reason the original build
did not.

### How an app is addressed

A deployment publishes apps one of two ways, and GET /api/v1/config reports which
via "base_domain", "path_prefix" and "domain_template". Read it rather than
assuming, because the answer changes what a URL looks like.

- **A hostname per app** (path_prefix empty): an app with id "shop" is served at
  shop.<base_domain>. Its "hostname" is "shop.<base_domain>" and its "url" adds a
  scheme.
- **One host, one path per app** (path_prefix set): every app shares
  <base_domain> and the path says which is meant, so "shop" is served at
  <base_domain><path_prefix>/shop.

Either way, an app can override its own hostname by setting "domain" when it is
created or updated, in which case it is served at that host's root.

The prefix is stripped before a request reaches the app, so an app served under a
prefix sees the same paths it would see if it were at the root. A
"X-Forwarded-Prefix" header tells it where it is mounted, which is what it needs
to build correct absolute links.

In the API, an app's "hostname" is the host and "path" the path under it — so
with a path prefix, the two together are the address and neither alone is. The
"url" field is the whole thing, scheme included, and is empty until the app has
been deployed.

### One namespace for everything

Every app is deployed into the same namespace the service itself runs in. That is
what lets it hold a namespaced Role rather than a ClusterRole — it has no
permission anywhere else in the cluster, so the blast radius of a bug here is the
apps it manages rather than every workload you run.

The trade is that a namespace no longer separates one app from another. Its
objects are told apart by an applab.io/app label, which every object it creates
carries and every query filters by. Deleting an app removes its objects and
leaves the rest alone; the pods and events endpoints report one app's workload,
not the namespace's.

GET /api/v1/config reports which namespace this is, as "namespace".

### applab's record versus the cluster

Applab keeps a record of what it last did — which commit it deployed, whether
the build succeeded — but **the cluster is the source of truth for what is
running**. When the two disagree, believe the cluster. An app reporting
"running" while its pods are crash-looping means the last thing applab recorded
was a successful rollout and something has happened since; the pod and event
endpoints are how you see that.

## Authentication

There is no user store. **An API key is the whole identity**: presenting a
configured key means you may do anything this deployment can do.

Send it on every request that needs one:

    Authorization: Bearer <key>

A bare key with no `Bearer ` prefix also works, for a caller pasting one in by
hand. A key is **never** accepted as a query parameter or a form field — URLs are
written to access logs, kept in shell history and sent in Referer headers, so a
credential placed in one leaks by default.

There is one tier. A key that authenticates can also delete, so treat it the way
you would treat any credential that can destroy data.

`GET /health`, `GET /api/v1/config` and `GET /llms.txt` need no key, because a
liveness probe cannot hold one and a caller has to be able to find out what this
service is before it can authenticate to it. Everything else does.

## API reference

Every route below is relative to this deployment's base URL, which
`GET /api/v1/config` reports as `api_base_url`. _(`key` means the route
requires `Authorization: Bearer <key>`; `no key` means it does not.)_

- `GET /health` — Liveness. No key required — a Kubernetes probe cannot hold one. _(no key)_
- `GET /metrics` — Prometheus metrics for this deployment, as text. No key required — a scraper holds one awkwardly and these numbers describe the platform rather than any app. Restrict this path at the network edge where that matters. _(no key)_
- `GET /api/v1/config` — This deployment's limits and capabilities. No key required, so it doubles as the cheapest reachability check. _(no key)_
- `GET /api/v1/version` — Build version and commit. _(no key)_
- `GET /api/v1/overview` — The platform at a glance: app counts by status, build counts and the most recent builds across every app, whether the cluster is configured and reachable, and this deployment's self-description. Counts exclude deleted apps. _(key)_
- `GET /api/v1/describe` — Everything needed to work with this deployment, in one call: a one-line summary, how to reach it, what it is wired to (registry, gateway, domains), what the presented key may do, every app with its address, and the shortest call for each operation. Start here; the full contract is /llms.txt. _(key)_
- `GET /llms.txt` — This document. _(no key)_
- `GET /api/v1/apps` — List apps. `?include_deleted=true` also returns apps that were deleted but whose id is still reserved. _(key)_
- `POST /api/v1/apps` — Create an app. Body: `{id, name?, port?, replicas?, dockerfile?, domain?}`. _(key)_
- `GET /api/v1/apps/{app}` — One app. _(key)_
- `PATCH /api/v1/apps/{app}` — Change an app's settings: `{name?, port?, replicas?, dockerfile?, domain?}`. Fields omitted are left alone. _(key)_
- `DELETE /api/v1/apps/{app}` — Delete the app and everything applab recorded for it. `?keep_source=true` retains the git repository. Requires an admin key: an app key may manage its app but not destroy it. _(key)_
- `GET /api/v1/apps/{app}/config` — The app's configuration: environment variables with their values, and the *names* of its secrets. Secret values are never returned by any route. _(key)_
- `PUT /api/v1/apps/{app}/env` — Set environment variables. Body: `{env: {"NAME": "value"}}`. Names not mentioned are left alone. `PORT` is refused — it is derived from the app's `port`. _(key)_
- `DELETE /api/v1/apps/{app}/env/{name}` — Remove one environment variable. _(key)_
- `PUT /api/v1/apps/{app}/secrets` — Set secret values. Body: `{secrets: {"NAME": "value"}}`. Names not mentioned are left alone. The response lists names only, never values. 501 if this deployment has no cluster, where secrets are kept. _(key)_
- `DELETE /api/v1/apps/{app}/secrets/{name}` — Remove one secret. _(key)_
- `GET /api/v1/apps/{app}/key` — The app's API key, in full. Works with the app's own key or an admin key. This key may be used for the API, the CLI and the console, and reaches only this app. 501 if this deployment has no cluster, where keys are kept. _(key)_
- `POST /api/v1/apps/{app}/key/rotate` — Replace the app's API key, invalidating the previous one immediately. Also creates one for an app that has none, so a lost key is recovered here. Returns the new key. _(key)_
- `POST /api/v1/apps/{app}/source` — Upload source as a tar or tar.gz and commit it. This is the main way to push code. Send the archive as the raw request body (`--data-binary @-`), or as `multipart/form-data` with a `file` field. `?message=` sets the commit message; `?parent=<sha>` commits onto a chosen commit instead of the current tip. A single wrapping directory is stripped, so `tar czf - myproject` lands with its contents at the root. _(key)_
- `GET /api/v1/apps/{app}/commits` — An app's commit history, newest first, with the current tip. `?limit=` (default 50). _(key)_
- `GET /api/v1/apps/{app}/commits/{sha}` — One commit. `{sha}` may be an abbreviated id. _(key)_
- `POST /api/v1/apps/{app}/source/uploads` — Begin a chunked upload for source too large for one request. Body: `{total, chunk_size, message?}`. Returns an `upload_id`. _(key)_
- `PUT /api/v1/apps/{app}/source/uploads/{upload}/parts/{index}` — Send one part. Body is the raw bytes. `{index}` is 1-based. Parts may be sent in any order and retried. _(key)_
- `POST /api/v1/apps/{app}/source/uploads/{upload}/complete` — Assemble every part and commit the result. Fails if any part is missing. _(key)_
- `POST /api/v1/apps/{app}/builds` — Build an image from a commit. Body `{commit_sha?}` — omit it to build the current tip. Returns immediately; the build runs as a Job in the cluster. Returns 501 if this deployment cannot build. _(key)_
- `GET /api/v1/apps/{app}/builds` — An app's builds, newest first. `?limit=` (default 20). _(key)_
- `GET /api/v1/apps/{app}/builds/{build}` — One build. Its status is read from the cluster, so it reflects the Job rather than what applab last recorded. _(key)_
- `GET /api/v1/apps/{app}/builds/{build}/logs` — The build's log, as `text/plain`. Follows the build while it runs and ends when it finishes; works unchanged for a build that has already finished. `?follow=false` returns what exists so far and stops. _(key)_
- `POST /api/v1/apps/{app}/deploy` — Deploy a commit and return the URL it is served at. Body `{commit_sha?, build?}` — omit `commit_sha` to deploy the current tip. If that commit has a successful build its image is reused; if it has none, the call fails with 409 and names the fix unless `build:true` was passed, in which case a build is started and the response is a 202 with the build. Returns 501 if this deployment cannot deploy. _(key)_
- `POST /api/v1/apps/{app}/rollback` — Deploy an earlier commit. Body `{commit_sha}` (required). Reuses that commit's existing image and never builds, so a rollback stays fast and cannot fail for a reason the original build did not. _(key)_
- `GET /api/v1/apps/{app}/status` — An app's live state in the cluster alongside what applab recorded. The two are reported separately and deliberately not reconciled: when they disagree, the cluster is right. _(key)_
- `POST /api/v1/apps/{app}/restart` — Roll the running pods, keeping the same image. For picking up a changed ConfigMap or recovering pods that are wedged. _(key)_
- `POST /api/v1/apps/{app}/stop` — Stop the app by removing its Deployment, Service and Ingress. The source and history are kept, so starting again is a deploy rather than a re-upload. _(key)_
- `GET /api/v1/apps/{app}/pods` — The app's pods, newest first, with per-container state. A pod that is not Running carries the reason — `CrashLoopBackOff`, `ImagePullBackOff` — and a crash loop's cause is reported from the *previous* container, since the current one is only restarting. `?limit=` (default 100, max 1000). _(key)_
- `GET /api/v1/apps/{app}/logs` — A pod's log as `text/plain`. Follows the pod by default; `?follow=false` returns what exists and closes. `?pod=` and `?container=` narrow it (default: the newest pod and the app container). `?previous=true` reads the previous container instance — where a crash loop's reason is written. `?tail=` (default 500, max 10000), `?since=` a duration such as `5m`. _(key)_
- `GET /api/v1/apps/{app}/events` — Recent Kubernetes events for the app, warnings first, with a `warnings` count. This is what explains a pod that never started: a failed scheduling, an image pull that was refused, a probe that killed the container. `?limit=` (default 50). _(key)_
- `GET /api/v1/apps/{app}/diagnose` — Why the app is not working, in one call: pods, events and the relevant log, ordered so the most likely cause comes first. Use this before reading the other four endpoints. _(key)_
- `GET /api/v1/apps/{app}/source/archive/{sha}` — Internal. Download a commit's source as a tar.gz. Authenticated with a single-use source token (issued when a build starts) rather than the API key, so a build job holds no credential that reaches beyond its own commit. _(no key)_

## Errors

Every failure is JSON with a meaningful HTTP status, never a 200 carrying a
failure:

    { "error": "human readable reason", "retryable": false }

**Branch on the HTTP status.** `retryable` is an additional signal for the cases
where a status alone is ambiguous — 409 and 503 are each sometimes worth
retrying and sometimes not, and guessing wrong means either giving up on a
transient failure or hammering a permanent one.

| Status | Meaning | What to do |
|---|---|---|
| 400 | The request is malformed | Fix the request; retrying will not help |
| 401 | Missing or unrecognised key | Check the `Authorization` header |
| 403 | Authenticated but not permitted | Nothing to retry |
| 404 | No such app, build or commit | Check the id |
| 409 | Conflicting state, or the resource already exists | Read the current state and decide |
| 413 | Body too large | Use the chunked upload endpoints |
| 500 | A bug in applab | Retry once, then report it |
| 503 | This deployment is shedding load or cannot reach the cluster | Back off briefly and retry |

A success is the payload under `data`:
```
    { "data": { ... } }
```
There is no `code` or `success` field to check — a 2xx means the call worked.
