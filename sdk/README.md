# AppLab SDKs

Language clients for the AppLab API, generated from [`api/openapi.yaml`](../api/openapi.yaml).

There are two, for the languages a caller is most likely to arrive with:

| Language | Directory | Package |
|---|---|---|
| Python | [`sdk/python`](python) | `applab_sdk` |
| TypeScript / JavaScript | [`sdk/typescript`](typescript) | `@applab/sdk` |

Go does not need one — [`internal/client`](../internal/client) *is* the Go client, and `applab-cli` is built on it.

## Generated, and not

Everything under `sdk/*/apis`, `sdk/*/models` and the runtime is generated by
[openapi-generator](https://openapi-generator.tech/) from `api/openapi.yaml`.
**Do not edit those by hand**: they are rewritten whenever the specification
changes, and the rewrite is what keeps them true to the API.

What is *not* generated is a small hand-written layer in each language — see
[The hard four](#the-hard-four) below. Those files are listed in each
`.openapi-generator-ignore`, so regeneration never touches them.

## The hard four

A code generator turns one API operation into one method, which is exactly right
for most of this API and wrong for four things. Each SDK adds them by hand:

| Helper | Why the generator cannot do it |
|---|---|
| `push_directory` / `pushDirectory` | Packs a directory. That is a client concern, not an API operation. |
| `upload_source_chunked` / `uploadSourceChunked` | The server needs the part count *before* the first part arrives, so the part size comes from a separate call to `/api/v1/config` and the archive has to be staged first. A one-request method for `POST /source` cannot. |
| `stream_logs` / `streamLogs` | `follow=true` is a response that may never end. A generated method reads the body to its end, which would hang. |
| `resolve_build_id` / `resolveBuildId` | Turns the abbreviated build id a person copied off a screen into the full one, and refuses when it is ambiguous rather than guessing. |

Without these, an SDK can list, create, delete and read state, but it cannot push
source and it cannot follow a log — which are the two things most callers want.

## Using one

The helper functions below are verified against a stub deployment; the generated
client's own class and method names come from openapi-generator and are whatever
it derives from `api/openapi.yaml` — read the generated `README` in each
directory once the workflow has produced it.

The helpers take an address and a key, so they need nothing from the generated
client:

```python
from applab_ext import push_directory, stream_logs

url = "https://applab.example.com/applab"
key = os.environ["APPLAB_KEY"]

push_directory(url, key, "shop", "./shop")

# follow the log as it arrives — a plain client would buffer a stream that may
# never end
for line in stream_logs(url, key, "shop", follow=True):
    print(line, end="")
```

```ts
import { pushDirectory, streamLogs } from "@applab/sdk/applabExt";

const url = "https://applab.example.com/applab";
const key = process.env.APPLAB_KEY!;

await pushDirectory(url, key, "shop", "./shop");

for await (const line of streamLogs(url, key, "shop", { follow: true })) {
  process.stdout.write(line);
}
```

For everything else — listing apps, reading status, deploying — use the generated
client for your language; it is configured with the same two things (the base URL
and `Authorization: Bearer <key>`).

## This is not published

The SDKs are committed to this repository, not released to PyPI or npm. They
exist so a caller in Python or TypeScript has something to read and use without
waiting for a release pipeline; installing one means pointing `pip` or `npm` at
the directory.

If they are ever published, the package names above (`applab_sdk`, `@applab/sdk`)
are the intended ones — but nothing here reserves them, so check before adopting
either.

## Regenerating

The SDK trees are rebuilt by [`.github/workflows/sdk.yml`](../.github/workflows/sdk.yml)
whenever `api/openapi.yaml` changes, and that workflow commits the result. The
generator is pinned to an exact version with a checksum, because its output is not
identical across versions and an unpinned one would make the drift check fail on a
day nobody changed anything.

To change the specification itself, edit the route table — not the YAML:

```sh
make gen-openapi   # regenerate api/openapi.yaml from the route table
```

`api/openapi.yaml` is generated from AppLab's route table and its Go types, and a
test fails if it is out of date. That generator is pure Go, so it runs on any
machine with a Go toolchain. Regenerating the *language SDKs* needs Java (that is
what openapi-generator is), which is why CI does that part rather than a laptop.

## What the SDKs do not cover

- **Git.** Cloning and pushing source is git's own protocol at `/git/<app>.git`,
  not a JSON route. It is documented in the specification so a client can see that
  it exists and that it takes HTTP Basic auth (the password is an API key), but no
  generated method wraps it. Use `git` itself, or `push_directory`, which uploads
  an archive over HTTP instead.
- **Following a log through the generated client.** Use `stream_logs` /
  `streamLogs`; the generated method is fine for `follow=false` only.
