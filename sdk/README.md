# AppLab SDKs

Language clients for the AppLab API, generated from [`api/openapi.yaml`](../api/openapi.yaml).

| Language | Directory | Package |
|---|---|---|
| Go | [`sdk/golang`](golang) | `github.com/shaowenchen/applab/sdk/golang` |
| Python | [`sdk/python`](python) | `applab_sdk` |
| TypeScript / JavaScript | [`sdk/typescript`](typescript) | `@applab/sdk` |
| Java | [`sdk/java`](java) | `com.applab:applab-sdk` |
| Rust | [`sdk/rust`](rust) | `applab-sdk` |

**Go has two clients, and they are not the same thing.**
[`internal/client`](../internal/client) is AppLab's own client, used by
`applab-cli`; it lives under `internal/`, so nothing outside this module can
import it. The SDK here is the generated, public one — for an application that
wants to call AppLab's API from its own Go program. Use `internal/client` if you
are working inside this repository, and `sdk/golang` if you are not.

## Generated, and not

Everything the generator produces — the API classes, the models, the runtime — is
generated by [openapi-generator](https://openapi-generator.tech/) from
`api/openapi.yaml`. **Do not edit those by hand**: they are rewritten whenever the
specification changes, and the rewrite is what keeps them true to the API.

What is *not* generated is a small hand-written layer in each language — see
[The hard four](#the-hard-four) below. Those files are listed in each
`.openapi-generator-ignore`, so regeneration never touches them.

## The hard four

A code generator turns one API operation into one method, which is exactly right
for most of this API and wrong for four things. Each SDK adds them by hand, named
in its own language's idiom:

| What it does | Why the generator cannot | Names |
|---|---|---|
| Packs a directory and pushes it | A client concern, not an API operation — and in every language it means deciding what counts as part of the tree | Go `PushDirectory` · Python `push_directory` · TS `pushDirectory` · Java `pushDirectory` · Rust `push_directory` |
| Uploads in parts | The server needs the part count *before* the first part arrives, so the part size comes from a separate call to `/api/v1/config` and the archive has to be staged first | Go `UploadChunked` · Python `upload_source_chunked` · TS `uploadSourceChunked` · Java `uploadSourceChunked` · Rust `upload_source_chunked` |
| Reads a log incrementally | `follow=true` is a response that may never end; a generated method reads the body to its end and would hang | Go `StreamLogs` · Python `stream_logs` · TS `streamLogs` · Java `streamLogs` · Rust `stream_logs` |
| Resolves an abbreviated build id | A lookup plus a conflict check rather than one call, and it refuses an ambiguous prefix rather than guessing | Go `ResolveBuildID` · Python `resolve_build_id` · TS `resolveBuildId` · Java `resolveBuildId` · Rust `resolve_build_id` |

Without these, an SDK can list, create, delete and read state, but it cannot push
source and it cannot follow a log — which are the two things most callers want.

## Dependencies, by language

Four of the five need nothing installed beyond a compiler. Rust does, and
that is the standard library's doing rather than a choice:

| Language | Runtime dependencies |
|---|---|
| Python | none — standard library only |
| TypeScript | none — `fetch` and Node built-ins |
| Go | none — standard library only |
| Java | none — the JDK's own `java.net.http` (the generator's `native` library) |
| Rust | `reqwest`, `serde`, `serde_json`, `tokio`, `futures-util` — but these are what the generated crate already depends on, not extra ones this SDK adds |

Rust is the odd one only because its standard library has no HTTP client at all.
Everything else it needs — including packing the directory — is written against
the standard library in every language, the tar writer included: Go, Java and Rust
each write the format out rather than taking a library for it, so that a
regenerated tree needs no dependency added by hand.

The one thing installed anywhere is `@types/node` for the TypeScript compile
check. It is types only — nothing reaches a user's runtime — and it is installed
by `hack/sdk-compile.sh` rather than declared in the SDK's `package.json`, because
that file is a generator deliverable that regeneration rewrites.

## Using one

The helper functions below are verified against a stub deployment; the generated
client's own class and method names come from openapi-generator and are whatever
it derives from `api/openapi.yaml` — read the generated `README` in each
directory once the workflow has produced it.

The helpers take an address and a key, so they need nothing from the generated
client:

```python
from applab_ext import push_directory, stream_logs

url = "https://applab.example.com/applab"
key = os.environ["APPLAB_KEY"]

push_directory(url, key, "shop", "./shop")

# follow the log as it arrives — a plain client would buffer a stream that may
# never end
for line in stream_logs(url, key, "shop", follow=True):
    print(line, end="")
```

```ts
import { pushDirectory, streamLogs } from "@applab/sdk/applabExt";

const url = "https://applab.example.com/applab";
const key = process.env.APPLAB_KEY!;

await pushDirectory(url, key, "shop", "./shop");

for await (const line of streamLogs(url, key, "shop", { follow: true })) {
  process.stdout.write(line);
}
```

For everything else — listing apps, reading status, deploying — use the generated
client for your language; it is configured with the same two things (the base URL
and `Authorization: Bearer <key>`).

## This is not published

The SDKs are committed to this repository, not released to PyPI or npm. They
exist so a caller in Python or TypeScript has something to read and use without
waiting for a release pipeline; installing one means pointing `pip` or `npm` at
the directory.

If they are ever published, the package names above (`applab_sdk`, `@applab/sdk`)
are the intended ones — but nothing here reserves them, so check before adopting
either.

## Regenerating

The SDK trees are rebuilt by [`.github/workflows/sdk.yml`](../.github/workflows/sdk.yml)
whenever `api/openapi.yaml` changes, and that workflow commits the result. The
generator is pinned to an exact version with a checksum, because its output is not
identical across versions and an unpinned one would make the drift check fail on a
day nobody changed anything.

To change the specification itself, edit the route table — not the YAML:

```sh
make gen-openapi   # regenerate api/openapi.yaml from the route table
```

`api/openapi.yaml` is generated from AppLab's route table and its Go types, and a
test fails if it is out of date. That generator is pure Go, so it runs on any
machine with a Go toolchain. Regenerating the *language SDKs* needs Java (that is
what openapi-generator is), which is why CI does that part rather than a laptop.

**Generate and check the language SDKs in Actions, not on a laptop.** Run the
[`sdk` workflow](../.github/workflows/sdk.yml) — push, or `workflow_dispatch` —
and let it do the generating, the compiling and the committing. Do not install a
JDK locally to produce a tree by hand: the generator runs in CI against a pinned
version and checksum, and a tree built with a different one is drift the moment
it lands. This is the rule, not a preference — a locally generated SDK is a tree
that has to be regenerated anyway, and the compile check that protects the commit
only runs where the workflow runs it.

The workflow **compiles** what it generated, because the drift check cannot see a
broken tree — a specification change can produce code that matches the spec byte
for byte and does not build. That compile step (and `hack/sdk-compile.sh` behind
it) exists for CI, where every toolchain is present; it is there so a broken tree
is caught before the commit, not as a local command to run in its place.

A generated tree cannot be checked into a state that fails to compile *and* pass,
because the workflow compiles before it commits. What it cannot do is run: the
SDK trees are not exercised against a live deployment by any automated test. The
hand-written helpers are — Go's have a test suite
([`sdk/golang/applabext`](golang/applabext/applabext_test.go)) that runs in
`make check`, and the Python and TypeScript helpers were exercised against a stub
deployment when they were written. The generated clients themselves are compiled,
not driven.

## What the SDKs do not cover

- **Git.** Cloning and pushing source is git's own protocol at `/git/<app>.git`,
  not a JSON route. It is documented in the specification so a client can see that
  it exists and that it takes HTTP Basic auth (the password is an API key), but no
  generated method wraps it. Use `git` itself, or `push_directory`, which uploads
  an archive over HTTP instead.
- **Following a log through the generated client.** Use `stream_logs` /
  `streamLogs`; the generated method is fine for `follow=false` only.
